# RMIS Physical PostgreSQL Schema Blueprint v1

Status: Proposed for schema approval  
Depends on: `database-design-review-v1.md`  
Source boundaries: `source-boundaries-v1.md`  
Target: Laravel 13, PHP 8.3, PostgreSQL, database per tenant

## 1. Purpose and boundary

This document converts the approved architecture into a migration-ready physical schema catalogue. It fixes database ownership, table relationships, keys, important constraints, indexes, state boundaries, and migration order. It does not yet create Laravel migrations and it does not invent provider-specific or statutory fields that require external contracts.

The physical design has three independent database types:

1. `landlord`: global identity, tenant registry, subscriptions, platform billing, provisioning and ELTECH control-plane data.
2. `tenant`: one operational PostgreSQL database for exactly one tenant, containing all of that tenant's branches and business data.
3. `tenant_reporting`: one reporting database/read store paired with one tenant; populated asynchronously and never used as the transaction source of truth.

There are no foreign keys between these databases. Cross-database references use immutable UUIDs and are validated by application workflows. All foreign keys inside one database use bigint IDs.

## 2. Physical conventions

### 2.1 Standard entity columns

Unless a table definition says otherwise, an API-addressable entity has:

```text
id              bigint generated by default as identity primary key
uuid            uuid not null
created_at      timestamptz not null
updated_at      timestamptz not null
```

Add `unique (uuid)`. Laravel generates UUIDv7 before insert. Internal foreign keys never use UUID. Pure pivot, immutable line, and internal queue tables need no UUID unless an external message or audit record addresses them.

Laravel 13's built-in `HasUuids::newUniqueId()` returns `Str::uuid7()`, but the unmodified trait treats the model primary key as the UUID column. Because RMIS retains a bigint primary key, shared module models use an RMIS `HasPublicUuid` trait that returns `['uuid']` from `uniqueIds()`, generates `(string) Str::uuid7()`, and returns `uuid` from `getRouteKeyName()`. Bulk inserts, imports and database seeders that bypass model events must supply UUIDv7 explicitly. Do not use `gen_random_uuid()` as the public-ID default because it generates UUIDv4.

### 2.2 Data types

| Purpose | PostgreSQL type |
|---|---|
| Money | `numeric(19,4)` |
| Stock, recipe and UoM quantities | `numeric(20,6)` |
| Rates and percentages | `numeric(12,6)` with domain-specific checks |
| Public identifier | `uuid` |
| Date/time | `date` and `timestamptz` |
| Currency | `char(3)` using ISO 4217 code |
| Country | `char(2)` using ISO 3166-1 alpha-2 code |
| Phone | normalized E.164 string, normally `varchar(20)` |
| Email/domain/code | normalized lowercase value plus original display value when needed |
| Provider extensions | bounded `jsonb`; never core relational data |

Enable `citext` where case-insensitive uniqueness is required and `pg_trgm` only for indexed server-side contains search. Enable `pgcrypto` only for a separately documented cryptographic requirement; it is not the RMIS public UUID generator.

### 2.3 Referential actions

- Use `restrict` for financial, stock, payroll, order and audit parents.
- Use `cascade` only for true owned details such as draft order-line modifiers or role assignment pivots.
- Use `set null` only for optional attribution such as a deactivated user snapshot where the transaction remains valid.
- Do not soft-delete ledgers, payments, receipts, payroll results or journals. Correct them with reversals.
- Master records referenced by transactions are deactivated, not deleted.

### 2.4 Transaction snapshots

Names, codes, tax rates, prices, quantities, currency, recipe version, provider references and accounting dimensions that explain a completed transaction are snapshotted on its header/lines. Historical reports must not depend on today's mutable master data.

## 3. Landlord database

### 3.1 Global identity and tenant access

| Table | Required columns and relationships | Important constraints/indexes |
|---|---|---|
| `users` | standard entity; `first_name`, `middle_name`, `last_name`, `display_name`, optional `email`, `email_normalized`, optional `phone`, `phone_normalized`, nullable `password`, separate email/phone verification timestamps, `status`, `password_changed_at`, `token_version` | unique partial normalized email/phone when non-null; check at least one login identifier exists; index `status`; password is global authentication only |
| `user_identities` | `user_id`; `provider`, `provider_subject`, email/name/avatar snapshots, `provider_verified`, `linked_at`, `last_used_at`, metadata | unique `(provider, provider_subject)`; unique `(user_id, provider)`; never identify Google by email |
| `tenant_accounts` | standard entity; `user_id`, `tenant_id`, `status`, `is_owner`, invitation fields, `joined_at`, `ended_at`, `token_version` | unique `(user_id, tenant_id)`; indexes `(tenant_id, status)` and `(user_id, status)` |
| `tenant_account_invitations` | standard entity; `tenant_id`, email/phone normalized, `invited_by_tenant_account_uuid`, token hash, expiry, accepted/revoked timestamps | unique active invitation per tenant/contact using partial index; never store raw invitation token |
| `user_device_sessions` | standard entity; `tenant_account_id`, `device_uuid`, device name/type/platform, refresh-token hash, current/last JTI, IP/user-agent snapshots, `is_active`, activity/expiry/revocation fields | unique `(tenant_account_id) where is_active`; unique refresh-token hash; indexes `(tenant_account_id, is_active)` and expiry |
| `authentication_events` | immutable; optional `user_id`, optional `tenant_account_id`, event, result, provider, request/correlation ID, IP/device facts, occurred time | BRIN on occurred time after volume warrants; no secrets or raw tokens |

Login locks `tenant_accounts.id` before checking or replacing an expired device session. Issued JWTs carry `user.uuid`, `tenant_accounts.uuid`, `tenants.uuid`, session UUID, JTI and expiry. Branch permissions remain tenant-local and are not token claims.

Password login lets the user explicitly choose email or phone. The versioned contract is:

```json
{
  "login_type": "email",
  "login": "user@example.com",
  "password": "secret"
}
```

or:

```json
{
  "login_type": "phone",
  "login": "+255712345678",
  "password": "secret"
}
```

`LoginRequest` allows only `email` or `phone`, normalizes the selected value, and performs one indexed exact lookup on `email_normalized` or `phone_normalized`. Phone input is normalized to E.164 using the selected/default country; email is trimmed and case-normalized. The API returns the same safe invalid-credentials response for an unknown identifier, wrong password, or unusable account. Password reset and verification use the same explicit identifier type. Google continues to resolve `user_identities` by stable provider subject and may link to the same global user only through the approved account-link flow.

### 3.2 Tenant registry and database placement

| Table | Required columns and relationships | Important constraints/indexes |
|---|---|---|
| `tenants` | standard entity; legal/trading names, TIN/VRN, country, timezone, locale, currency, email/phone, status, lifecycle timestamps | unique normalized TIN/VRN when supplied; indexes `status`, `created_at` |
| `tenant_domains` | standard entity; `tenant_id`, normalized domain, type, primary flag, verification token hash/status/time, SSL status | globally unique domain; one primary active domain per tenant via partial unique index |
| `database_clusters` | standard entity; code, host, port, database server name, region, SSL mode, optional secret namespace, capacity/health/status | unique code; local may use `prefer`/`disable`, production should explicitly use `verify-full`; do not store tenant database passwords here |
| `tenant_databases` | standard entity; `tenant_id`, `database_cluster_id`, database name/username, password secret reference, status, primary flag, schema version and lifecycle timestamps | unique `(database_cluster_id, database_name)`; one primary active database per tenant; preserve retired rows |
| `tenant_provisioning_runs` | standard entity; `tenant_id`, requested by, target cluster, requested/started/completed times, status, current step, failure code/safe message | index `(tenant_id, created_at desc)` and `(status, created_at)` |
| `tenant_provisioning_steps` | `tenant_provisioning_run_id`, sequence, step code, status, attempts, timestamps, failure facts | unique `(run_id, sequence)` and `(run_id, step_code)` |
| `tenant_schema_versions` | `tenant_id`, database UUID, migration batch/name/checksum, applied time and result | unique `(tenant_id, migration_name)`; used for fleet drift, not as Laravel's tenant migration table replacement |

Moving a tenant changes the active `tenant_databases` placement record. The tenant UUID, accounts, domains and tenant-local public UUIDs do not change.

### 3.3 Packages, entitlements and limits

| Table | Required columns and relationships | Important constraints/indexes |
|---|---|---|
| `features` | standard entity; unique code, name, description, value type, status | codes such as `integrations.card_payments`; immutable code after use |
| `packages` | standard entity; code, name, billing interval, currency, price, status, version/effective dates | unique `(code, version)`; effective-date overlap validation |
| `package_features` | `package_id`, `feature_id`, enabled flag, optional numeric/text limit | unique `(package_id, feature_id)` |
| `tenant_subscriptions` | standard entity; `tenant_id`, `package_id`, status, trial/current-period/cancel/end timestamps, billing customer reference | index `(tenant_id, status)`; prevent overlapping active subscriptions by service rule/locking |
| `tenant_feature_overrides` | standard entity; `tenant_id`, `feature_id`, mode, optional value, reason, effective/expiry dates, approved by platform user | one current override per tenant/feature; fully audited |
| `tenant_usage_counters` | `tenant_id`, feature/metric code, period, value, measured time | unique `(tenant_id, metric_code, period_start)`; contains aggregates only |

An operational integration is enabled only when the landlord entitlement is active and its tenant-local `integration_accounts` record is active.

### 3.4 Platform operators, support and audit

Use a separate `platform_users` model and guard. Publish Spatie Permission tables with platform-specific names: `platform_roles`, `platform_permissions`, `platform_model_has_roles`, `platform_model_has_permissions`, and `platform_role_has_permissions`.

Additional tables:

- `support_access_grants`: tenant, platform user, requested/approved by, exact scope, reason, start/expiry/revocation; no permanent implicit support access.
- `support_impersonation_sessions`: support grant, tenant account being represented, session times, IP/device and reason.
- `platform_audit_entries`: append-only actor/action/subject/request facts, redacted before/after data, previous hash and entry hash.
- `platform_announcements` and `tenant_announcement_deliveries`: control-plane communication without tenant operational data.

### 3.5 ELTECH subscription billing

Keep these tables completely separate from restaurant customer payments:

- `platform_invoices`, `platform_invoice_lines`, `platform_credit_notes`;
- `platform_payment_providers`, `platform_provider_accounts`;
- `platform_payment_attempts`, `platform_transactions`, `platform_refunds`;
- `platform_webhook_receipts`, `platform_settlements`, `platform_settlement_lines`;
- `platform_reconciliation_runs`, `platform_reconciliation_items`.

Invoice numbers are unique by issuing ELTECH legal entity and fiscal year. Money rows carry currency. Provider event IDs, transaction references and attempt idempotency keys have provider/account-scoped unique constraints.

## 4. Tenant database

The tenant database contains no `tenant_id` column. Every branch-owned operation has `branch_id`. Tenant-wide masters have explicit branch override/assignment tables where necessary.

### 4.1 Organisation, access and configuration

| Table | Required columns and relationships | Important constraints/indexes |
|---|---|---|
| `companies` | standard entity; legal/trading identity, TIN/VRN, country, timezone, locale, base currency, contacts, status | normally exactly one active row; legal identity changes audited |
| `branches` | standard entity; code, name, contacts/address/geolocation, timezone, currency, status, opened/closed dates | unique code; indexed normalized name/search fields |
| `departments` | standard entity; optional parent, code, name, status | unique code; prevent cyclic hierarchy in service |
| `cost_centres` | standard entity; optional branch and parent, code, name, status | unique code; branch ownership checked where set |
| `locations` | standard entity; `branch_id`, optional parent, type, code, name, status | unique `(branch_id, code)`; hierarchy cannot cross branch |
| `branch_configurations` | standard entity; `branch_id`, configuration version, effective dates, close time, tax/receipt/order defaults | unique `(branch_id, effective_from)`; typed columns for operational rules |
| `business_dates` | standard entity; `branch_id`, business date, status, opened/closed by and timestamps | unique `(branch_id, business_date)`; one open row per branch via partial unique index |
| `tenant_users` | standard entity; immutable `tenant_account_uuid`, immutable `base_user_uuid`, display and normalized name/email/phone snapshots, status, last synchronized time | unique tenant-account/base-user UUIDs and unique normalized email/phone when present; no password |
| `tenant_user_branches` | `tenant_user_id`, `branch_id`, status, primary flag, valid dates, assigned/revoked by | unique `(tenant_user_id, branch_id)`; indexes branch/status and user/status |
| `user_department_access` | `tenant_user_id`, `department_id`, optional branch, valid dates | unique active assignment; explicit scope, not a permission name |

Spatie Teams uses tenant tables `roles`, `permissions`, `role_has_permissions`, `model_has_roles`, and `model_has_permissions`, with `branch_id` as the team key on assignments. Roles/permissions are dynamically managed but protected system permission codes cannot be renamed or removed while referenced. Exact permission examples are `products.create`, `payments.refund`, and `billing.receipts.reprint`.

### 4.2 Audit, approvals and idempotency

- `audit_entries`: immutable UUID, sequence, branch, actor tenant user, action, subject type/UUID, correlation/request IDs, IP/device, redacted before/after JSON, previous hash, entry hash, occurred time.
- `audit_chain_anchors`: chain range/hash, anchored time and external anchor reference.
- `approval_requests`: branch, type, subject type/UUID, amount/currency, requested by, status, expiry, version.
- `approval_steps`: request, sequence, required permission/rule, assigned/acted by, decision, reason, timestamp.
- `idempotency_records`: scope, actor/client, key, request hash, response status/body reference, expiry; unique `(scope, actor_key, idempotency_key)`.
- `outbox_messages`: aggregate/event UUIDs, type, payload, status, attempts, available/processed times; unique event UUID and partial pending index.
- `inbox_messages`: source, external message ID, payload hash, state, attempts/times; unique `(source, external_message_id)`.

Audit JSON is an evidence snapshot, not the primary database for business fields. Sensitive values are redacted before hashing.

### 4.3 Taxes, numbering and accounting dimensions

- `tax_profiles`, `tax_rates`, `tax_rate_components`, with effective dates and no overlap for the same tax code/jurisdiction.
- `branch_tax_registrations`: branch certificate, business-licence, fiscal location/device and tax-office references with effective dates; company TIN/VRN are not duplicated here.
- `document_sequences`: branch, document type, business date/fiscal year, current value and formatting pattern; unique by scope and locked for allocation.
- `currencies` and `exchange_rates`: base/quote, rate source, applicable timestamp; unique by pair/source/time.
- `payment_terms`, `fiscal_periods`, `accounting_dimensions`, and `accounting_dimension_values`.

Rates and legal rules are effective-dated. Completed transaction lines snapshot the applied rate, basis and calculated amounts.

### 4.4 Terminals, printers and documents

- `terminals`: branch, unique branch code, type, device identity/public key, status, last seen, configuration version.
- `printer_agents`: branch, machine/public-key identity, credential rotation metadata, status and last seen.
- `printers`: branch, printer agent, code/name, connection type/identifier, model, paper width, capabilities, status.
- `printer_routes`: branch, optional terminal/station, document type/channel, printer, priority, copies, active flag; unique route priority within its scope.
- `document_templates` and `document_template_versions`: type, locale, versioned content/hash and effective status.
- `receipt_documents`: immutable bill/payment/fiscal snapshots, number, template version, content hash, object path and issue metadata.
- `print_jobs`: receipt/document, route/printer, requested by, copy number, idempotency key, status and lifecycle times.
- `print_job_attempts`: job, agent/printer, attempt number, acknowledgement/error and timing.
- `receipt_reprints`: original receipt, copy number, reason, requested/approved by and audit UUID.

Unique `(receipt_document_id, copy_number, printer_id)` prevents duplicate printing jobs. A print failure never reverses payment.

### 4.5 Product, menu, price, recipe and promotions

Core masters:

- `units_of_measure`, `uom_conversions`;
- `product_categories`, `products`, `product_translations`, `product_barcodes`, `product_images`;
- `menus`, `menu_categories`, `menu_category_products`, `product_branch_settings`;
- `modifier_groups`, `modifiers`, `product_modifier_groups`, `modifier_group_options`;
- `combos`, `combo_components`, `combo_component_options`;
- `price_lists`, `price_list_branches`, `price_list_items`;
- `recipes`, `recipe_versions`, `recipe_lines`, `sub_recipes`;
- `product_cost_snapshots`, `availability_overrides`;
- `promotions`, `promotion_rules`, `promotion_actions`, `promotion_branch_assignments`.

Important rules:

- Product SKU and barcode uniqueness is explicit and tenant-wide unless the business approves a branch-specific namespace.
- UoM conversion factor is positive; ambiguous duplicate conversion paths are forbidden.
- A recipe version becomes immutable once activated or used.
- Effective-dated price list items and branch settings cannot overlap for the same product/scope.
- Promotion evaluation stores deterministic applied-rule snapshots on the order/bill; it is not recalculated historically.
- Search indexes cover normalized SKU, barcode and name; trigram indexes are added only to the user-facing contains-search columns.

### 4.6 Floor, reservations and service sessions

- `floor_areas`, `restaurant_tables`, `table_seats`;
- `table_sessions`, `table_session_tables`, `table_session_guests`;
- `reservations`, `reservation_tables`, `reservation_status_histories`, `reservation_deposits`;
- `waitlist_entries`, `waitlist_status_histories`;
- `service_charges` and `service_charge_rules`.

Table code is unique within a branch. A table has at most one active table session, enforced by a partial unique index. Reservation overlap/capacity is protected by a transaction that locks candidate tables; PostgreSQL exclusion constraints may be used once the final reservation time model is fixed.

### 4.7 Orders, kitchen, billing and payments

Transaction spine:

- `orders`: branch/business date, order number, channel, table session/customer/waiter/terminal, currency, statuses, totals, opened/closed times and version.
- `order_lines`: order, product/recipe snapshot, quantity, unit price, tax, discounts, totals, course/station and status.
- `order_line_modifiers`, `order_line_status_histories`, `order_status_histories`, `order_amendments`.
- `kitchen_stations`, `station_routing_rules`, `kitchen_tickets`, `kitchen_ticket_lines`, `preparation_events`, `courses`.
- `bills`, `bill_lines`, `bill_allocations`, `applied_discounts`, `applied_promotions`.
- `payment_methods`, `payments`, `payment_allocations`, `tips`, `payment_refunds`, `payment_refund_allocations`.
- `fiscal_receipts`, `fiscal_receipt_events`.

Critical constraints:

- unique `(branch_id, business_date, order_number)` and `(branch_id, business_date, bill_number)`;
- all quantities and monetary allocations are non-negative except explicit reversal lines;
- sum of active bill allocations cannot exceed the source order-line amount;
- sum of payment allocations cannot exceed the captured payment or payable bill balance;
- a payment/refund uses an idempotency key unique within its method/provider account;
- paid bills are immutable except through refund/credit/reversal workflows;
- inventory consumption is emitted once when an eligible order line enters the configured production state; reversal has its own unique link to the original consumption.

Status changes lock the aggregate row and validate a state transition table/service. Reverb events are emitted only from committed outbox records.

### 4.8 Cashier and cash control

- `cash_drawers`, `cashier_sessions`, `cash_movements`, `cash_counts`, `cash_count_lines`;
- `cash_variances`, `cash_variance_approvals`, `shift_reports`.

Use a partial unique index for one open cashier session per drawer and, if required, one open cashier session per user/branch. Every cash movement has a business date, reason/type, currency, amount, actor and immutable reference. Closing locks the session, totals recorded movements, preserves the blind count and posts approved variance through journals.

### 4.9 Inventory, production and costing

- `inventory_items`, `inventory_item_branch_settings`, `stores`, `storage_bins`;
- `stock_batches`, `stock_ledger_entries`, `stock_ledger_allocations`;
- `stock_balances` as a transactionally maintained projection, never the audit source;
- `stock_counts`, `stock_count_lines`, `stock_adjustments`;
- `stock_transfers`, `stock_transfer_lines`, `stock_transfer_receipts`;
- `production_runs`, `production_inputs`, `production_outputs`, `yield_records`;
- `recipe_consumptions`, `recipe_consumption_lines`, `consumption_reversals`;
- `waste_events`, `waste_lines`, `waste_approvals`;
- `cost_layers`, `inventory_valuation_snapshots`.

Stock ledger entries are append-only and have item, store, optional bin/batch, base-unit quantity, unit cost, total cost, movement type, business reference and occurred time. Unique `(source_type, source_uuid, source_line_key, movement_type)` enforces idempotent posting. Negative-stock policy is branch/item-specific and checked under row locks. Index hot reads by `(store_id, inventory_item_id, occurred_at desc)` and batch expiry for FEFO.

### 4.10 Procurement, supplier and accounts payable

- `suppliers`, `supplier_contacts`, `supplier_products`, `supplier_branch_assignments`;
- `purchase_requisitions`, `purchase_requisition_lines`, approval links;
- `requests_for_quotation`, `rfq_suppliers`, `supplier_quotes`, `supplier_quote_lines`;
- `purchase_orders`, `purchase_order_lines`, `purchase_order_status_histories`;
- `goods_receipts`, `goods_receipt_lines`, `goods_receipt_inspections`;
- `supplier_invoices`, `supplier_invoice_lines`, `supplier_invoice_matches`;
- `landed_costs`, `landed_cost_allocations`;
- `supplier_payments`, `supplier_payment_allocations`, `supplier_credit_notes`.

PO, receipt and invoice lines retain ordered/received/invoiced quantities and price/tax snapshots. Matching records explain tolerances and discrepancies. Posted supplier invoices and payments are corrected by credit/reversal, not edits. Supplier invoice number is unique per supplier/legal company where supplied.

### 4.11 Financial accounting

- `chart_of_accounts`, `account_branch_settings`, `journal_sources`;
- `journal_entries`, `journal_lines`, `journal_reversals`;
- `posting_rules`, `posting_rule_versions`, `posting_rule_lines`;
- `bank_accounts`, `bank_statement_imports`, `bank_statement_lines`;
- `bank_reconciliation_runs`, `bank_reconciliation_matches`;
- `budgets`, `budget_lines`, `fixed_assets`, `asset_depreciation_runs` where enabled.

Each posted journal is immutable and balanced per currency: total debit equals total credit and every line has exactly one debit or credit amount. Unique `(source_type, source_uuid, posting_event)` prevents double posting. Fiscal-period state is checked while holding an appropriate lock. Reversal journals point to originals; an original can have only the allowed reversal chain.

### 4.12 Staff, attendance, payroll, tips and commissions

Employment setup:

- `employees`, `employee_contacts`, `employment_contracts`, `employee_branch_assignments`;
- `positions`, `employee_departments`, `employee_cost_centres`;
- `rosters`, `roster_shifts`, `attendance_events`, `attendance_summaries`;
- `leave_types`, `leave_requests`, `leave_balances`, `employee_loans`, `employee_loan_schedules`;
- `commission_rules`, `commission_earnings`, `tip_pools`, `tip_pool_allocations`.

Payroll core adapted from CFS:

- `pay_items`;
- `statutory_rules`, `statutory_rule_bands`;
- `employee_payroll_profiles`, `employee_salary_histories`, `employee_recurring_pay_items`;
- `payroll_periods`, `payroll_runs`, `payroll_run_employees`, `payroll_run_lines`;
- `payroll_run_exports`, `payroll_payments`, `payroll_payment_allocations`;
- `payroll_postings`, `payroll_reversals`.

Salary, recurring pay and statutory rules are effective-dated without overlaps. A payroll run snapshots employee identity, branch, department, cost centre, contract, rate, attendance/overtime/leave, applied statutory version/band, taxable basis and every earning/deduction/employer contribution. Approved/posted runs are immutable. Payment and journal posting use unique source-event keys. Statutory seed data remains outside structural migrations and requires country/legal approval.

### 4.13 Customers, loyalty, gift value and campaigns

- `customers`, `customer_contacts`, `customer_addresses`, `customer_consents`, `customer_merge_records`;
- `loyalty_programs`, `loyalty_accounts`, `loyalty_ledger_entries`, `loyalty_redemptions`;
- `gift_instruments`, `gift_value_ledger_entries`;
- `customer_segments`, `campaigns`, `campaign_recipients`, `campaign_delivery_events`;
- `feedback_entries`, `complaint_cases`.

Normalized phone/email uniqueness follows the tenant's customer deduplication policy; do not blindly reject households or recycled phone numbers. Loyalty and gift balances are projections of append-only ledgers. Every earn/redeem/expire/reverse entry has a unique source key. Consent is purpose/channel/version-specific with obtained/withdrawn evidence.

### 4.14 Delivery and digital ordering

- `delivery_zones`, `delivery_rates`, `drivers`, `driver_assignments`;
- `deliveries`, `delivery_status_histories`, `delivery_proofs`, `cod_reconciliations`;
- `digital_channels`, `digital_carts`, `digital_cart_lines`, `digital_orders`;
- `aggregator_orders`, `aggregator_order_events`, `aggregator_product_mappings`.

Digital and aggregator orders feed the same internal `orders` aggregate. Unique `(integration_account_id, external_order_id)` prevents duplication. Status ownership, rejection/cancellation deadlines, commission, tax and payout facts are preserved as provider snapshots.

### 4.15 Tenant integrations

- `integration_providers`: adapter code/type/name/status.
- `provider_capabilities`: provider and capability code/configuration.
- `integration_accounts`: provider, optional default branch, environment, merchant reference, encrypted configuration/secret reference, webhook key reference, status and activation audit.
- `integration_account_branches`: account, branch, status and branch-specific reference/configuration.
- `payment_attempts`: bill/order, account, amount/currency, idempotency key, request state and expiry.
- `provider_transactions`: attempt/account, external reference, type/state, amounts/fees, provider times and redacted response facts.
- `webhook_receipts`: account, external event ID, signature result, payload hash/object path, processing state/times.
- `provider_refunds`: original provider transaction, optional internal payment refund, amount, reason/state and provider references.
- `provider_settlements`, `provider_settlement_lines`.
- `provider_reconciliations`, `provider_reconciliation_items`.

Unique keys are scoped to `integration_account_id`, because two tenants or merchant accounts may receive the same provider reference. Credentials and raw sensitive payloads do not appear in audit logs. Webhooks store verified evidence first and process asynchronously.

### 4.16 Notifications and media

- `notification_templates`, `notification_template_versions`, `notification_preferences`;
- `notifications`, `notification_recipients`, `notification_delivery_attempts`;
- Media Library tenant tables using a tenant-connection Media model and tenant-prefixed private object keys.

Notification idempotency is unique by business event, recipient and channel. Provider delivery status is append-only. Uploaded objects store content hash, detected MIME type, size, scan status and retention classification; API responses use short-lived signed URLs.

## 5. Reporting database per tenant

The first reporting schema should be dimensional and derived, not a copy used for writes:

- dimensions: date, time, branch, product, menu category, customer, employee, supplier, channel, tender, inventory item and accounting dimension;
- facts: order line, payment, discount, kitchen duration, stock movement, waste, procurement, payroll, journal and delivery;
- `reporting_checkpoints`: source stream/LSN or outbox sequence, processed time and lag;
- `metric_definitions`: versioned formula, grain, currency/timezone treatment and owner;
- `report_refresh_runs`: status, source watermark, started/completed time and errors.

Every fact keeps source UUIDs for drill-through and `occurred_at`, `business_date`, `loaded_at` and source version. A report displays its as-of watermark. Deletion/privacy events are propagated without breaking required financial retention.

## 6. Required invariant and index register

The migration implementation must include, at minimum:

| Invariant/query | Database enforcement |
|---|---|
| One account for one human in a tenant | unique `tenant_accounts(user_id, tenant_id)` |
| One active device per tenant account | partial unique index on active `user_device_sessions` |
| One active primary tenant database | partial unique index on `tenant_databases(tenant_id)` |
| One open business date per branch | partial unique index on active/open `business_dates(branch_id)` |
| One open table session per table | partial unique index on active `table_session_tables(table_id)` |
| One open cashier session per drawer | partial unique index on open `cashier_sessions(cash_drawer_id)` |
| No duplicated order/bill number | unique branch/business-date/document number |
| Provider callback deduplication | unique account/external event ID plus payload hash |
| Payment request deduplication | unique account/idempotency key |
| Stock posting exactly once | unique source/source UUID/source line/movement type |
| Accounting posting exactly once | unique source/source UUID/posting event |
| Balanced posted journal | deferred constraint trigger or posting procedure plus service transaction |
| Effective-date non-overlap | exclusion constraint where practical, otherwise locked validation transaction |
| Queue hot-path performance | partial indexes on pending outbox/inbox/print/notification jobs |
| Operational listing | scope/status/date composite indexes aligned with versioned API filters/order |
| Search | normalized btree prefix indexes; selective trigram GIN for approved contains fields |

Every foreign key used in joins receives an explicit index. Collection endpoints default to 15 rows and cap page size at 100; high-volume ledgers, audit, orders and events use cursor pagination with a stable `(occurred_at, id)` or `(created_at, id)` order.

## 8. Migration implementation rules

1. Create extensions and referenced parents before children.
2. Give every constraint and index a deterministic explicit name.
3. Add check constraints for status, positive quantities, currency consistency and mutually exclusive debit/credit values.
4. Add foreign-key indexes in the same migration as the foreign key.
5. Use database transactions for normal schema changes; isolate PostgreSQL operations that cannot run in a transaction.
6. Do not seed roles, permissions, statutory rates or provider credentials in structural migrations. Use versioned idempotent seeders/catalogue commands.
7. Provision a new tenant by create database -> run all tenant migrations -> seed protected permissions/catalogues -> create company/first branch -> project owner tenant user -> assign branch -> set Spatie team -> assign owner authorization -> activate placement.
8. Record migration checksum/version in the landlord after the tenant database migration commits.
9. Test fresh landlord, fresh tenant and upgrade paths independently. Include constraint, rollback, concurrency and idempotency tests for critical invariants.
10. Never expose internal IDs, secret references, credential configuration or raw provider payloads through API resources.
