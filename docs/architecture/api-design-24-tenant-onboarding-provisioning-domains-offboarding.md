# API Design 24: Tenant Onboarding, Provisioning, Tenant Database Creation, Domains, Migration, Seeding, and Offboarding

Project: Restaurant POS ERP  
Backend: Laravel, PHP 8.3, PostgreSQL, database-per-tenant multitenancy  
API version: v1  
Date: 2026-08-25

## 1. Purpose

This design explains tenant lifecycle:

```text
registration/onboarding
tenant registry creation
tenant database creation
tenant migrations
tenant seeders
default domain
custom domain verification
activation/suspension/offboarding
```

Architecture:

```text
database per tenant
landlord registry controls tenant DB location/status
tenant business data lives only in tenant DB
```

## 4. Registration first-release fields

Public registration should collect only necessary fields.

Recommended:

```text
business_name
first_name
last_name
email or phone
password
```

Defaults:

```text
country_code = TZ
timezone = Africa/Dar_es_Salaam
currency_code = TZS
locale = en
phone country code = +255
```

Do not require:

```text
TIN
VRN
legal/trading split
custom domain
```

Those can be completed later.

## 5. Tenant creation timing

After registration:

```text
Create landlord tenant record
Create tenant account/member owner
Create provisioning run
Queue tenant provisioning job
Return provisioning status to frontend
```

Tenant DB is generated by provisioning job after landlord tenant record exists.

Do not create tenant DB before landlord registry exists.

## 6. Tenant database naming

Confirmed pattern:

```text
rmis_tenant_000001
rmis_tenant_000002
```

Keep 6-digit suffix for database names.

Human document numbers use short padding like:

```text
ORD-2026-01
REC-2026-01
```

Database names and business document numbers are different concerns.

## 7. Provisioning steps

Recommended steps:

```text
validate_request
create_tenant_record
assign_subscription
select_database_cluster
create_database_credentials
create_tenant_database
run_tenant_migrations
seed_tenant_defaults
create_company
create_default_branch
create_owner_tenant_user
assign_owner_permissions
create_default_domain
activate_tenant
```

Each step should be recorded in `tenant_provisioning_steps`.

If a step fails, resume/retry from the failed step when safe.

## 8. Database clusters

`database_clusters` defines where tenant databases live.

Fields:

```text
host
port
region
ssl_mode
secret namespace
status
```

Local development:

```text
ssl_mode = prefer or disable
```

Production:

```text
ssl_mode = require/verify-ca/verify-full depending infrastructure
```

Do not hard-code one server forever. Clusters allow tenant DBs to move later.

## 9. Tenant databases

`tenant_databases` stores physical database details.

Important fields:

```text
tenant
database cluster
database name
database username
password secret reference
status
is primary
schema version
provisioned/activated/retired timestamps
```

Only one active primary DB should exist per tenant.

## 10. Domains

`tenant_domains` supports:

```text
platform_subdomain
custom
```

Default idea:

Use platform-hosted domain first.

Example:

```text
{tenant-slug}.app-domain.com
```

But the platform base domain should come from app configuration/environment where the system is hosted.

Do not ask tenant for custom domain during first registration.

Custom domain requires external DNS/SSL configuration.

## 11. Domain verification token

For custom domain:

```text
Generate random token
Store hash in verification_token_hash
Ask tenant to add DNS TXT record
Verify TXT record
Mark verified
Provision SSL
```

Store only token hash.

For platform subdomain:

No external DNS verification is usually needed if wildcard DNS is configured by platform.

## 12. Tenant statuses

Tenant statuses:

```text
provisioning
trial
active
suspended
expired
offboarded
```

Meaning:

- `provisioning`: DB/setup in progress
- `trial`: tenant usable during trial
- `active`: tenant fully active
- `suspended`: restricted access
- `expired`: subscription/trial expired
- `offboarded`: tenant closed/exported/retired

## 13. Provisioning run statuses

Recommended:

```text
pending
running
completed
failed
cancelled
```

Migration currently stores status as string without check constraint. Add check later for consistency.

## 15. Complexity

Simple:

- tenant list/details
- domain list
- provisioning status

Medium:

- public registration
- admin tenant create
- custom domain verification

High:

- DB creation
- migration/seeding
- retry failed provisioning
- tenant DB move
- offboarding

Queue required:

- tenant DB provisioning
- tenant migrations
- tenant seeding
- domain verification/SSL
- offboarding export

## 16. Offboarding

Offboarding flow:

```text
suspend tenant
backup tenant DB and media
export data if required
disable domains
mark tenant offboarded
retire tenant database after retention period
```

Never immediately delete tenant DB without backup/export policy.
